# K4.6 수동 채팅 전송

## 공식 계약

[공식 채팅 전송](https://developers.spooncast.net/docs/api-reference/chat): POST /v1/live/chat, Bearer 인증과 application/json, 본문은 message 문자열 하나다. 방송 식별자를 보내는 자리는 없으며 OAuth 토큰이 DJ의 방송을 정한다. 메시지는 UTF-16 code unit 200개 이하, 빈 문자열/공백만 있는 메시지는 금지다. 성공은 본문 없는 204다. DJ가 작성해도 SPOON에는 봇 계정 이름으로 게시된다. 자신의 봇 발화는 자신의 SSE로 돌아오지 않으므로 모니터에 가짜 발화를 추가하지 않는다.

401은 인증, 403은 권한 또는 얼림/채팅 금지(OAPI_MNGR_0208)/입장 차단(OAPI_MNGR_0209), 404 OAPI_MNGR_0301은 방송 없음, 429는 방송 공용 전송 한도 또는 API 한도다. 400은 내용/길이/요청 오류다. 5xx와 연결 실패는 보수적으로 결과 불확실로 취급한다. 공식 멱등성 키, 정확한 숫자 호출 한도, 단독 UTF-8 인코딩 특례는 확인되지 않았다. HTTP JSON의 표준 UTF-8을 사용하며 임의 요청 필드를 추가하지 않는다. Retry-After가 있으면 기존 공통 파서로 준수한다.

## 구조 및 권한

ChatSendService는 기존 LiveReadClient.http, 타임아웃·프록시 금지·리디렉션 금지, RealAuthService의 토큰 lease/갱신을 재사용한다. 별도 OAuth/HTTP 저장소를 만들지 않는다. 새 동의 scope에 chat.send를 추가하되 기존 토큰은 변경하지 않는다. 권한이 없으면 해당 기능만 차단하고 사용자의 직접 재동의를 안내한다.

현재 인증 브라우저 세션과 토큰에 결합된 GET /v1/live로 방송을 확인한다. isChatFrozen이 누락되면 상태 미확인으로 차단하며 true면 전송하지 않는다. 현재 DJ의 토큰이 방송을 정한다는 공식 계약을 사용하고 영구 DJ ID를 생성·추정하지 않는다. 준비 때 확인한 liveId와 전송 직전 ID가 달라지면 거절한다. POST 성공 후 다시 방송 상태를 확인한다. API가 liveId를 받지 않으므로 조회와 POST 사이의 방송 전환을 원자적으로 막는 보장은 없다.

## 로컬 API와 보안

- GET /api/live/chat/prepare: 현재 방송·권한 확인 뒤 유효시간 300초의 일회용 로컬 request_id를 발급한다. 이 GET은 채팅을 보내지 않는다.
- POST /api/live/chat: application/json, csrf/message/request_id/notice=confirmed만 허용한다. notice는 봇 게시·입장 고지 이해에 대한 명시적 확인이다.
- 기존 로그인 브라우저 인증과 Host/중복 쿠키 검사를 적용한다. 최대 4096바이트 JSON과 중복 키·타입을 검증한 뒤 CSRF만 가진 내부 form 요청으로 기존 post_values의 Origin/세션/CSRF 검사를 그대로 재사용한다. 인증 없음 401, 입력·CSRF·Origin 오류는 400이며 다른 전송 상태는 JSON state로 반환한다.

성공 상태 sent, sent_context_unverified, sent_broadcast_changed는 모두 공식 204를 받은 경우뿐이다. uncertain은 실제 게시됐을 가능성이 있으므로 확인 전 다시 보내지 말라는 안내다. 대기·권한·차단·요청 만료·중복·rate_limited 상태를 구분한다. 원본 오류 메시지를 반환하지 않는다.

## 중복·호출 보호

서버가 발급한 티켓을 요청·방송·브라우저 세션에 결합하고, 실제 transport 호출 전 소비한다. 최대 32개 티켓과 128개 메시지 지문만 메모리에 유지한다. 같은 메시지의 최근 시도는 60초간 차단하고 실제 POST 시도 간 최소 3초의 로컬 간격을 둔다. 이는 공식 제한이 아니라 앱 보호 정책이다. 진행 중에는 다른 전송을 busy로 거절한다.

POST는 정확히 한 번 시도하며 401/429/5xx/timeout에 자동 재전송하지 않는다. 401이면 기존 토큰 갱신을 시도할 수 있지만 POST는 다시 보내지 않는다. 취소/타임아웃에서도 이미 소비한 티켓을 되살리지 않는다. 브라우저가 응답을 잃었을 때도 입력을 유지하고 전송 결과 불확실을 알린다. 서버 재시작·세션 교체·보존 시간 밖에서는 완전한 중복 방지를 보장하지 않는다. 공식 멱등성 지원을 추정하지 않는다.

## UI와 보존

/broadcast에 봇 계정 채팅 패널을 추가했다. 사용자가 전송 준비 확인을 누른 뒤 메시지를 작성하고 고지 확인 및 전송 버튼을 눌러야 게시된다. textarea의 Enter/Shift+Enter는 줄바꿈이며 Enter 자동 발송은 없다. UTF-16 글자 수는 JavaScript 문자열 length로 표시하고 서버에서도 utf-16-le 바이트 수로 검증한다. 성공 시 입력을 비우고 실패/불확실 시 유지한다. 재시도는 새로운 수동 준비 절차가 필요하다. 기존 채팅·하트·청취자·팬 UI를 유지한다.

메시지·작성자·실패 원문을 SQLite에 저장하거나 로그에 출력하지 않는다. 메모리에는 메시지 원문 대신 SHA-256 지문과 만료 정보만 보관한다. OAuth token/Secret/cookie는 브라우저에 보내지 않는다. CSP를 완화하지 않았다. 자동 응답/예약/반복 전송/방송 제어는 없다.

## 검증과 실제 방송 확인

자동 검증은 소켓 차단, 가상 토큰, Mock HTTP Transport와 임시 DB만 사용한다. 204, 권한, 방송 대기·변경·얼림, UTF-16/공백/JSON/본문 한도, CSRF/Origin/Host/다른 브라우저, 요청 재사용·메시지 반복, 401/403/404/429/5xx/timeout과 자동 재전송 없음, 입력·불확실성 유지 및 기존 회귀를 검증한다. CSS에 HTML이 섞인 손상은 기존 스타일 응답 테스트에서 탐지되어 복구했다.

Chrome 수동 확인: http://localhost:8000/broadcast에서 글자 수/이모지, Enter 줄바꿈, Tab 포커스, 권한 부족·방송 없음, 중복 클릭, 성공·불확실 입력 처리와 콘솔/CSP를 확인한다. 실제 Chrome과 실제 전송은 실행하지 않았다.

실제 방송 검증은 별도 사용자 승인 및 수동 단계다. 필요시 chat.send에 직접 재동의 → 봇 이름 게시·방송 입장 고지 확인 → 방송 진행/얼림 해제 확인 → 사용자 직접 단일 메시지 작성·전송 → SPOON 화면에서 게시 확인. 모니터에 자신의 메시지가 돌아오지 않는 것은 정상이다. 불확실한 응답은 게시를 먼저 확인하며 자동 재전송하지 않는다.

K4.7 제안: 실제 수동 전송의 권한·고지·불확실성 검증을 먼저 마친 뒤 별도 승인 아래 자동화 범위·사용자 중지·쿨다운·중복·관측 누락 정책을 설계한다. 이번 단계에서 자동화는 구현하지 않았다.

최종 검증: pytest -q -W error 410 passed. JavaScript 상태·문법 검사, pip check, git diff --check와 CSS 손상 검사가 통과했다. 실제 API/로그인/SSE/채팅 전송, 운영 DB 변경, 커밋·push는 수행하지 않았다.
