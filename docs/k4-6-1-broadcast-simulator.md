# K4.6.1 격리된 방송 시뮬레이터

## 실행

```sh
.venv/bin/python -m spoon_local --simulator
```

브라우저: http://localhost:8000/broadcast

실제 앱과 별도 프로세스·애플리케이션이다. 같은 8000 포트를 사용하므로 기존 서버가 실행 중이면 사용자가 먼저 중지해야 한다. 기존 서버를 자동 중지하거나 실제 연결을 변경하지 않는다. 기본 실행은 기존 동작이며 --simulator를 명시해야 한다. --real-oauth/--mock-auth와 동시에 선택할 수 없고 DB 경로 인자도 거절한다. 바인딩은 127.0.0.1이다.

## 격리와 네트워크

create_simulator_app은 환경 설정·토큰·HTTP 클라이언트·DB 경로 인자를 받지 않는다. RealOAuthClient/RealSSESource를 생성하거나 실제 앱 factory를 호출하지 않는다. .env를 읽지 않으며 앱에는 실제 OAuth/SSE 연결 라우트가 없다. 같은 로컬 API 이름이라도 시뮬레이터 인스턴스의 메모리 처리 함수로만 연결된다. 일반 앱에는 /api/simulator 제어 API가 등록되지 않는다.

CLI에서 process-local socket connect/connect_ex/UDP sendto와 DNS 해석에 loopback-only 가드를 설치한다. 브라우저의 로컬 서버 접속은 허용한다. 이는 Python 네트워크 경로 보호이며 OS 수준의 네트워크 namespace나 악의적 native 코드를 격리하는 sandbox라고 주장하지 않는다. 코드 구조 자체에도 외부 HTTP 전송 경로가 없으며 테스트에서 실수로 외부 연결이나 실제 factory 호출이 생기면 실패하도록 차단한다.

첫 브라우저가 시뮬레이터 세션을 소유한다. HttpOnly/SameSite=Lax 쿠키와 CSRF, 정확한 localhost Host, 중복 쿠키·Origin 검사를 적용한다. 다른 브라우저는 제어·데이터 조회를 거절한다. 현재 브라우저에서 새로고침하면 메모리에 남아 있는 상태를 볼 수 있다. 쿠키를 잃은 경우 서버를 재시작해야 한다. 실제 OAuth 로그인은 필요하지 않다.

## 처리 경로 재사용

가상 SSE 바이트 → 기존 SSEParser(7바이트 분할로 한글/CRLF 검증) → 기존 normalize_donation 또는 RealtimeBuffer → 메모리 후원 ledger/채팅/하트 집계 순서다. DonationRepository의 기존 append/recent, HMAC 지문과 명시 ID 중복 방지, 기존 청취자·팬 normalize와 전송 validate_message를 재사용한다. 실제 네트워크 수집 컨트롤러/토큰 갱신은 사용하지 않는다.

SQLite는 sqlite3.connect(':memory:')뿐이다. 기존 Mock 스키마를 메모리에서 사용하며 실제·Mock 파일 DB조차 열지 않는다. 사용자 지정 경로나 운영 파일을 주입할 수 없다. 초기화는 이 메모리 객체만 폐기·재생성한다. 운영 SQLite 마이그레이션은 없다. 원문 채팅/가상 전송은 SQLite에 저장하지 않는다.

## 모델과 기능

liveId는 sim-live-0001 같은 명백한 테스트 형식이다. 사용자 ID는 sim-user-*이고 닉네임은 [가상] 접두사를 사용한다. SSE ID는 기존 파서 호환을 위한 합성 숫자-offset이며 실제 SPOON ID가 아니다. API의 simulation=true와 항상 보이는 상단 배너로 구분한다.

방송 시작/종료/변경, 입장/퇴장, 채팅/하트/후원, 중복 재생·잘못된 이벤트, 연결 끊김/재연결, 가상 401/403/429/500/timeout/불확실 전송을 제어할 수 있다. 방송 변경 시 청취자·현재 팬·채팅/하트 컨텍스트를 초기화하고 가상 후원 저장 기록은 해당 시뮬레이터 메모리에만 유지한다. 현재 방에서 나간 청취자는 가상 팬 랭킹에서 제외한다. 하트는 공식 형식의 totalAmount를 사용한다.

한 명령 최대 100개, 최대 이벤트 시도 5000개, 가상 청취자 100명, 가상 회차 1000개다. 한도를 넘으면 초기화가 필요하다. 채팅 버퍼는 기존 100개/5분, 중복 버퍼는 2048개/5분 제한이다. 한도에 닿은 일괄 명령은 일부만 생성될 수 있으며 결과 집계의 actual/processed와 cap을 확인한다.

## 시나리오

- A: 방송 시작, 5명 입장, 채팅 10개, 하트, 후원 3개, 종료.
- B: 30명, 채팅 100개, 하트·후원 30개씩.
- C: 연결 단절·재연결, 중복 재생, 정상 이벤트.
- D: 권한/만료/호출 제한/서버 오류, 방송 종료.

각 단계 간 0.5초이며 실행/중지/초기화가 가능하다. 중지는 task를 취소하고 완료를 기다린 뒤 반환하므로 이후 추가 이벤트가 생기지 않는다. 초기화는 먼저 중지한다. 오류 복구 버튼은 가상 오류 플래그만 해제하며 실제 재인증이나 네트워크 연결은 하지 않는다.

결과 패널에는 생성/처리 건수, 보존된 채팅 수, 관측 하트 수량, 저장 후원 건수·스푼 합계, 현재 청취자, 중복 제거, 파싱 실패, 마지막 이벤트, 한도와 시나리오 실행 여부를 표시한다. 보존된 채팅 수가 생성 건수보다 작은 것은 버퍼·TTL·권한 초기화 때문일 수 있다.

## UI 및 가상 전송

기존 스튜디오 템플릿·화이트/오렌지 스타일·채팅/하트·청취자/팬·전송·후원 검색 UI를 재사용한다. 시뮬레이터에만 제어 패널과 고정 배너를 주입한다. 실제 앱 템플릿에 가짜 데이터를 삽입하지 않는다. 시뮬레이터용 스타일은 별도 simulator.css이며 기존 CSS 손상 검사를 유지한다.

가상 POST는 실제 chat sender/HTTP transport를 호출하지 않는다. 입력 검증, 소유 세션/CSRF/Origin/고지 확인, 일회용 티켓, 반복 메시지·연속 전송 보호를 거쳐 모의 204/실패 결과를 반환한다. 가상 성공 문구는 실제 게시와 명확히 구분한다. 자신의 가상 전송도 수신 채팅 목록에 임의 추가하지 않는다. 실패는 오류 플래그를 설정한 뒤 테스트할 수 있다. 모든 출력은 textContent이며 외부 이미지·폰트·JS가 없다.

## 한계와 수동 확인

이 모드는 실제 서버의 전송 결과·네트워크 백오프·OAuth 교환·속도 제한·방송 입장 고지를 증명하지 않는다. 연결 상태와 오류는 수동 모델이며 실제 서비스의 HTTP 상태·토큰 회전은 기존 Mock Transport 테스트에서 별도로 검증한다. 시나리오의 권한 오류는 공통 오류 플래그이며 모든 scope 조합 UI는 아직 제공하지 않는다. 실제 SPOON 계정/회차 귀속·완전한 이벤트 누락 복원도 검증하지 않는다.

Chrome에서 가상 배너, 방송 시작, 이벤트 생성, 청취자/팬 탭 조회, 가상 전송, 가상 후원 검색, 대량 100건, 중복·오류, 시나리오 중지·초기화와 콘솔/반응형을 확인한다. 이 작업에서 실제 Chrome은 실행하지 않았다.

K4.7 자동화는 우선 이 격리 모드에서 시나리오·쿨다운·중복·중지 정책을 검증하고, 실제 서비스 연결은 별도 승인과 명시적 사용자 설정으로만 진행하는 것을 권장한다.

최종 검증: pytest -q -W error 425 passed. JavaScript 제어/XSS·문법, pip check, git diff --check, CSS와 신규 파일 공백 검사가 통과했다. 실제 Chrome·SPOON·OAuth·SSE·채팅·운영 DB는 실행/변경하지 않았고 커밋·push하지 않았다.
